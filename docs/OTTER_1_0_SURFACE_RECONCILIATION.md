## 10. Event system

Status: **decided** - SPEC-DECISIONS.md D121 (approved 2026-09-27).
The "current behavior" column is the behavior measured before the decision; see `docs/OTTER_1_0_EVENT_LOOP_REVIEW.md`.

| id | question | current behavior | decision |
|---|---|---|---|
| EV1 | Is cross-source fairness guaranteed or best-effort? | Fixed per-pass order (watcher, WebSocket, TCP/UDP, HTTP, jobs). No fairness guarantee; command jobs win under load. | Best-effort with eventual progress for ready sources. No equal-share, round-robin, maximum-latency or quantitative fairness guarantee. |
| EV2 | May one event source drain an unbounded queue before others run? | Yes for command jobs (while TryDequeue). | EV3 | Which event sources are dispatched during wait? | Only HTTP and command jobs. | EV4 | Is event ordering guaranteed only within a source? | FIFO within a source; unspecified across sources. | Ordered within a source; cross-source order unspecified. |
| EV5 | Are TCP/UDP receive callbacks allowed to be delayed by polling cadence? | Yes: two loop passes per UDP/TCP event and a 10 ms sleep that lasts about 16 ms on Windows (about 31 events/s). | Yes. Polling and scheduling delay are permitted; measured latency and throughput are runtime characteristics, not language semantics. |
| EV6 | Is the event loop cooperative rather than real-time? | Cooperative: handlers run to completion on one thread and are never preempted. | Yes. Cooperative: one handler at a time, run to completion, never preempting running Otter code; no real-time guarantee. |
